# Decision Log — B2B Order Management Platform

**Document version:** 1.0 (Phase 1 — Planning & Design)
Format: each entry records context, decision, alternatives considered, rationale, consequences, and the requirements it serves. Entries are immutable once accepted; superseding uses a new ID.

---

### D-01 · Layered monolith (single Express API) — **Accepted** (Phase 1)
- **Context:** Small v1 scope (single tenant, A-01/A-07); team familiarity; constraint C-02 mandates Express + layered structure.
- **Decision:** One deployable Express API organized in layers (routes/middleware/controllers/services/repositories) with module boundaries per domain (auth, catalog, cart, order, invoice, audit). One React SPA.
- **Alternatives:** Microservices (rejected — operational overhead far exceeds v1 needs); MVC without service layer (rejected — business rules would leak into controllers/repositories, breaking NFR-10 and testability).
- **Consequences:** Simple Docker topology; module boundaries must be policed in code review; extraction to services later remains possible.

### D-02 · Roles as `VARCHAR + CHECK` instead of PG `ENUM` or permissions table — **Accepted**
- **Context:** Three stable roles (admin/agent/customer); RBAC required (C-05, NFR-04).
- **Decision:** `users.role` varchar with CHECK constraint; authorization by role list per route in `authorize()` middleware; permission matrix documented in `requirements.md` §4.
- **Alternatives:** PG ENUM (rejected — awkward migrations); full `permissions`/`role_permissions` tables (rejected for v1 — YAGNI; migration path from CHECK to lookup table is cheap).
- **Consequences:** Role set changes require a migration of the CHECK constraint only; per-endpoint role map is testable (NFR-04).

### D-03 · PostgreSQL via Docker Compose with `node-pg-migrate` — **Accepted**
- **Context:** C-03 requires PostgreSQL + node-pg-migrate; environment audit showed Docker works via WSL2, no local `psql`.
- **Decision:** `db` compose service (postgres:16-alpine, named volume, healthcheck); migrations run by the `api` container on boot and available as `npm run migrate` locally against the same container. *(Superseded in Phase 13 — migrations now run in a dedicated one-shot `migrate` service, not on API boot; see **D-29**.)*
- **Alternatives:** SQLite for dev (rejected — reservation/locking semantics differ, tests would not reflect production); local PG install (rejected — absent on machine).
- **Consequences:** One-command startup (NFR-12); integration tests need `DATABASE_URL_TEST` pointing at a second database/schema.

### D-04 · JWT bearer tokens, 2 h expiry, per-request user re-check; no refresh rotation in v1 — **Accepted**
- **Context:** C-05 mandates JWT; statelessness aids D-01; deactivation must take effect (FR-AUTH-06).
- **Decision:** Access-only JWT (`sub`, `role`, `iat`, `exp`); `authenticate` middleware loads the user row (indexed PK) and rejects `is_active=false`. Short 2 h TTL limits staleness window.
- **Alternatives:** Session cookies (rejected — conflicts with C-05 and adds server state); refresh-token rotation (deferred — complexity not justified for v1 threat model); token blocklist (rejected — needs state anyway).
- **Consequences:** One extra indexed query per request (acceptable, NFR-05); logout is client-side token discard — documented limitation.

### D-05 · Backend-enforced RBAC; frontend guards cosmetic — **Accepted**
- **Context:** Project convention memory: "frontend guards are only for navigation."
- **Decision:** Every endpoint declares roles server-side; ownership filters (customer → own rows) applied in services; forbidden cross-owner reads return 404 not 403 (no existence leak, FR-ORD-11).
- **Consequences:** UI may hide buttons the API would also reject; tests must exercise the API directly (AC-AUTH-07, AC-LIF-05).

### D-06 · Stock reservation by decrementing `available_quantity` under `FOR UPDATE` row lock — **Superseded by D-18 (Phase 3)** (mechanism unchanged in spirit: lock + CHECK guard)
- **Context:** Overselling is the top business risk (R-01); FR-ORD-02; single stock column (A-02).
- **Decision:** At order creation, within one transaction: `SELECT … FOR UPDATE` the inventory rows (locked in product-id order to avoid deadlocks), check availability, decrement, write an `inventory_movements` reservation row. Cancel increments back. Fulfillment does not touch stock (reservation is consumed).
- **Alternatives:** Reservation ledger with on-hand vs. reserved columns (rejected for v1 — doubles complexity; revisit if partial fulfillment ships); optimistic check-without-lock (rejected — race window, fails AC-ORD-05); serialized transactions (rejected — throughput).
- **Consequences:** Brief row lock per product during ordering; DB CHECK `>= 0` as final guard; ledger reconciliation test proves correctness (database-design §5).

### D-07 · Historical snapshots in `order_items`; invoices generated from snapshots — **Accepted**
- **Context:** Catalog prices/names change; disputes and invoices must reflect what the customer agreed (FR-ORD-04, FR-INV-01).
- **Decision:** Copy `product_name`, `unit_price`, `tax_rate` into `order_items` at creation; invoices store their own denormalized totals and item lines. `products` is never consulted for past totals.
- **Alternatives:** Join-through-products (rejected — history mutates when catalog changes, breaking AC-ORD-06).
- **Consequences:** Minor storage duplication (negligible at A-07 scale); catalog edits provably cannot alter invoices (SC-04).

### D-08 · Persistent idempotency table scoped to `POST /api/orders`, 24 h retention — **Accepted**
- **Context:** Double-clicks, retry-after-timeout, and parallel duplicates threaten stock integrity (R-04, FR-ORD-06).
- **Decision:** Required `Idempotency-Key` header (client UUID); `UNIQUE(user_id, idempotency_key)` claim-row pattern; completed responses stored and replayed with `200`; concurrent duplicate on an `in_progress` key gets `409 DUPLICATE_REQUEST`. Cleanup job deletes rows past `expires_at` (24 h). A waiting-period instead of fail-fast for in-progress keys is reconsidered if pilots report confusion — tracked with OQ-03.
- **Alternatives:** In-memory map (rejected — lost on restart, per-instance); DB unique hash of payload (rejected — legitimate repeat orders would be blocked); applying idempotency to all POSTs (deferred — only order creation needs it in v1).
- **Consequences:** One extra table + periodic cleanup; SC-03 becomes measurable.

### D-09 · Money as `NUMERIC(14,2)` + integer-cent arithmetic in JS; half-up per line — **Accepted** (precision amended to `NUMERIC(12,2)` by D-17)
- **Context:** C-03/NFR-07; float errors cause incorrect totals (R-03).
- **Decision:** DB `NUMERIC`; service layer converts to integer cents (`Math.round(Number(x) * 100)` guarded by Zod's 2-decimal string format regex so input never carries float noise), does all sums in integers, rounds tax per line half-up (`cents * rate / 10000 …`), formats back via `(cents/100).toFixed(2)`. A `utils/money.js` module owns all conversions — no ad-hoc `+`/`*` on money elsewhere (enforced in review + unit tests).
- **Alternatives:** JS floating point (rejected — 0.1+0.2 problem); BigInt cents (acceptable but no benefit at this magnitude); `decimal.js` dependency (deferred — integer cents is sufficient and dependency-free; revisit if multi-currency lands).
- **Consequences:** Deterministic AC-CART-02 fixture values; totals invariant `grand = subtotal + tax` provable by unit tests.

### D-10 · Automatic invoice on fulfillment, sequential numbering via per-period counter row — **Accepted**
- **Context:** FR-INV-01/02; manual numbering error-prone.
- **Decision:** Fulfillment transaction inserts the invoice and obtains `invoice_number` from an `invoice_counters(period TEXT, next_val)` upsert (`INSERT … ON CONFLICT … RETURNING`) → gap-tolerant, race-safe, no advisory locks needed.
- **Alternatives:** `MAX(n)+1` select (rejected — race duplicates); sequence per month (rejected — PG sequences can't be scoped per period cleanly); UUID display (rejected — unprofessional for invoicing).
- **Consequences:** One more table; AC-INV-02 verifies monotonic numbers.
- *Note:* the counter table is an internal mechanism; `database-design.md` §1 diagram omits it for the user-facing entity set — add it in the Phase 2 migration checklist (already listed under §4 work in implementation plan M-02).

### D-11 · Single audit writer service; append-only table — **Accepted**
- **Context:** FR-AUD-01/02/05; secret-leak risk (R-06).
- **Decision:** All audit writes go through `AuditService.log(actor, action, entity, details)` called by domain services inside the same transaction as the business change; details keys whitelisted per action; no HTTP verbs or repository methods exist for update/delete of audit rows.
- **Alternatives:** Trigger-based auditing (rejected — captures storage diffs, not intent/roles; harder to exclude secrets); middleware-only logging (rejected — no entity linkage).
- **Consequences:** Audit rows commit/rollback with their business event (NFR-13); AC-AUD-02 greps for leaks.

### D-12 · Test runners: Node built-in (`node:test`) + Supertest backend; Vitest + RTL frontend; Playwright E2E — **Accepted**
- **Context:** C-08 mandates these tools.
- **Decision:** Unit tests target services/utils with repository stubs; integration tests boot `app.js` via Supertest against `DATABASE_URL_TEST` with per-suite migrate+truncate; E2E runs the compose stack. Coverage via `c8` for Node tests, V8 providers for Vitest.
- **Consequences:** Three test harnesses to wire in `package.json` scripts (see implementation plan Phase 3).

### D-13 · Admin-provisioned accounts only (no self-registration) — **Accepted, revisit post-pilot**
- **Context:** B2B relationships are pre-existing; scope boundary in `requirements.md` §3.2.
- **Decision:** No public signup; admins create customer/staff users with an initial password.
- **Alternatives:** Email-verified self-signup (deferred — requires mail infrastructure out of scope).
- **Consequences:** Pilot onboarding needs an admin; OQ list updated if pilot disagrees.

### D-14 · Defer: PDF invoices, email delivery, per-customer price lists, partial fulfillment, multi-warehouse — **Accepted (scope freeze)**
- **Context:** Scope boundaries (§3.2) to protect Phase 2–4 timeline.
- **Decision:** Explicitly out of v1; recorded here so "why isn't X there?" has one answer.
- **Consequences:** Revisit in a Phase 5/backlog planning cycle with pilot feedback.

### D-15 · Top-level layout `frontend/` + `backend/` (+ `database/`, `evidence/`) — **Accepted** (Phase 2)
- **Context:** The Phase 2 build instruction specified an explicit directory layout (`frontend/`, `backend/src/...`, `backend/migrations/`, `database/seeds/`, `evidence/screenshots/`, `evidence/test-reports/`) that supersedes the illustrative `client/`/`server/` naming used in the Phase 1 architecture sketch.
- **Decision:** Adopt the instructed names. Express API lives in `backend/` (CommonJS, `"type"` unset), React SPA in `frontend/` (`"type": "module"`). Seed SQL under `database/seeds/`; an `evidence/` tree stores real lint/build/test output and future screenshots. A thin root `package.json` provides orchestration scripts (`lint`, `test`, `build:frontend`, `format`) delegating via `npm --prefix`. Layer-for-layer responsibilities from `architecture.md` §4 are unchanged.
- **Alternatives:** Keeping `client/`/`server/` (rejected — conflicts with the explicit phase spec); npm workspaces (deferred — `--prefix` scripts keep installs isolated and simple for one developer).
- **Consequences:** `architecture.md` §4/§7 updated to as-built; the Phase 1 file-layout sketch is now annotated rather than treated as canonical. Backend uses CommonJS consistently per the instruction; frontend uses ESM (required by Vite).

### D-16 · Dev-time CORS strategy: Vite/nginx proxy over permissive CORS — **Accepted**
- **Context:** Landing page must call the health endpoint from the browser; requirement C-05/NFR-04 want RBAC later and the security section wants an explicit (non-wildcard) CORS allow-list.
- **Decision:** In local dev, Vite proxies `/api` → `http://localhost:4000`; in Docker, nginx proxies `/api` → `backend:4000`. Both make the API same-origin so no cross-origin request is made. The Express CORS middleware still enforces an explicit `CORS_ORIGINS` allow-list (empty by default = same-origin only), never `*`.
- **Alternatives:** Setting `CORS_ORIGINS=*` for convenience (rejected — violates security constraints); serving SPA from Express static (deferred — nginx/CDN serving is the documented target).
- **Consequences:** `backend/.env.example` and `frontend/.env.example` document the knobs; the health round-trip is exercised by the frontend Vitest test and the runtime smoke check.

### D-17 · Schema as-built: BIGSERIAL primary keys, `NUMERIC(12,2)` money, node-pg-migrate v7 — **Accepted** (Phase 3)
- **Context:** The Phase 3 instruction mandated consistent BIGSERIAL (or identity) primary keys and `NUMERIC(12,2)` money, and a consistently CommonJS backend; the Phase 1 design had sketched UUID + `NUMERIC(14,2)`.
- **Decision:** All surrogate PKs are `BIGSERIAL` (FK columns `BIGINT`); all money columns are `NUMERIC(12,2)` (max ±99,999,999.99 — ample for the A-07 scale and enforced by PostgreSQL overflow errors, integration-tested). `node-pg-migrate` is pinned to v7 because v9 is ESM-only and the backend must stay CommonJS; migrations are plain JS `up`/`down` files under `backend/migrations/`. Journal table: `pgmigrations`. The compose `db` service is published on host port **5433** because the development machine runs an unrelated native PostgreSQL service on 5432.
- **Alternatives:** UUIDv7 (rejected — explicit phase instruction); keeping v9 with `await import()` interop everywhere (rejected — extra friction, CLI tooling assumes CJS here); `GENERATED ALWAYS AS IDENTITY` (equivalent, but BIGSERIAL is the literal requirement — PostgreSQL 10+ makes them near-identical).
- **Consequences:** `docs/database-design.md` §1/§2/§4 and `docs/architecture.md` §5 updated to as-built; id columns in future API paths are integers.

### D-18 · Three-column stock model with a stored generated `available_quantity` — **Accepted** (Phase 3; amends D-06)
- **Context:** The Phase 3 instruction required the schema itself to define physical, reserved, and available stock and their constraints.
- **Decision:** `inventory(physical_quantity ≥ 0, reserved_quantity ≥ 0, available_quantity GENERATED ALWAYS AS (physical_quantity − reserved_quantity) STORED)` plus the hard guard `CHECK (physical_quantity − reserved_quantity ≥ 0)`. Reservations move `reserved`; fulfillment consumes both columns; receipts/corrections move `physical`. `available_quantity` is read-only at the DB level (writes raise SQLSTATE 428C9). The append-only `audit_logs` guarantee is enforced by a BEFORE UPDATE/DELETE trigger, not only by convention.
- **Alternatives:** Single `available_quantity` column (the Phase 1 sketch — rejected: cannot answer "on hand vs. committed" and physical losses become invisible); view instead of generated column (rejected: cannot carry the non-negative CHECK directly… it can, but the stored column keeps index/statistics simple).
- **Consequences:** Phase 4 ordering transactions update `reserved` (never `available`); overselling attempts fail at the CHECK with a clear constraint name (`inventory_available_non_negative`), covered by integration tests; `inventory_movements` remains the reconciliation ledger.

### D-19 · Auth token model: short JWT access + rotating opaque refresh in a strict cookie — **Accepted** (Phase 4; implements D-05)
- **Context:** The Phase 4 instruction required JWT auth with bcryptjs and Zod, short-lived access tokens, an HTTP-only/SameSite cookie strategy or a documented bearer alternative, CSRF awareness, rate limiting, and disabled-user enforcement. C-02 mandates `bcryptjs` (not `bcrypt`).
- **Decision:** Two-token model. (1) Access token: 15-min HS256 JWT (`sub/role/typ/iss/aud`), returned in the JSON body for **in-memory Bearer use** — never localStorage (XSS rationale documented in README “Security model”). (2) Refresh token: 256-bit opaque secret wrapped in a JWT envelope, stored **only as its SHA-256 hash** in `refresh_tokens` (migration 13), delivered exclusively via an `HttpOnly; SameSite=Strict; Path=/api/auth` cookie. `POST /api/auth/refresh` rotates it; reuse of a spent token revokes the whole `family_id` chain (theft detection). `logout` revokes the family. No CSRF token is needed because SameSite=strict blocks cross-site sending. Registration is CUSTOMER-only (strict Zod schema rejects any `role` field); ADMIN/ORDER_MANAGER come only from the controlled seed. `authenticate` re-loads the user each request so disabled accounts lose access immediately. Rate limiting: express-rate-limit v8 buckets (login/refresh 10 per 15 min, register 5 per 15 min per IP via `ipKeyGenerator`). JWT secrets come from env only — production boot fails on missing/short/dev-default secrets or `COOKIE_SECURE=false`.
- **Alternatives:** Cookie-only session (rejected — C-02 mandates JWT); access token also in a cookie (rejected — reopens CSRF on every API call); stateless-only refresh without DB rows (rejected — no revocation, no reuse detection, disabled-user kill-switch impossible); self-issued role in register with server override (rejected — fail-open risk; strict schema fails closed).
- **Consequences:** One extra table (`refresh_tokens`, 13 total) + hash-per-login writes; refresh expiry cleanup exists as `purgeExpired()` but is not yet scheduled (Phase 5 ops); the SPA must keep the access token in memory (Phase 6 UI work). express-rate-limit's in-memory store is per-instance — acceptable at A-02/A-08 scale, revisit with horizontal scaling.

### D-20 · Low-stock expressed as a per-product `inventory.low_stock_threshold` column — **Accepted** (Phase 5)
- **Context:** The Phase 5 instruction required a clearly defined low-stock threshold and a `GET /api/inventory/low-stock` feed for ADMIN/ORDER_MANAGER. A single global constant would be arbitrary and wrong for SKUs with different replenishment cadence.
- **Decision:** Add `inventory.low_stock_threshold integer NOT NULL DEFAULT 20 CHECK (>= 0)` (reversible migration 14). The rule is defined once in SQL: a product is **low-stock iff `available_quantity <= low_stock_threshold`**. The feed, the list `low_stock_only` filter, and the `is_low_stock` flag on every inventory row all use that same generated comparison, so no caller re-implements it. Settable at product create, via `PATCH /api/products/:id`, and via `PATCH /api/inventory/:id`.
- **Alternatives:** Global `env`/constant threshold (rejected — one number cannot fit fast- and slow-moving SKUs); a materialized/duplicated `is_low_stock` boolean column (rejected — would drift from `available_quantity`, which is itself generated; the comparison is cheap and always consistent); computing it only in application SQL fragments per query (rejected — the definition would leak across repositories and could diverge).
- **Consequences:** The public product row also carries `low_stock_threshold`/`physical_quantity`/`reserved_quantity` (the joined inventory columns); these are non-secret operational figures and are shown intentionally in the staff/admin tables. Default backfill of 20 keeps pre-existing rows meaningful without data migration.

### D-21 · List envelope `{data, meta:{page, limit, total}}`; page count derived client-side — **Accepted** (Phase 5)
- **Context:** Every paginated endpoint needed a consistent shape, and a browser bug surfaced during Phase 5 evidence when the SPA read a non-existent `meta.totalPages` and rendered “Page 1 of NaN”.
- **Decision:** Servers return only `meta.page`, `meta.limit`, `meta.total`. The page count is a pure function of `total` and `limit`, so it is derived once in the frontend (`frontend/src/utils/pagination.js`: `totalPages`/`pageSummary`) and never duplicated on the wire. A regression unit test guards the NaN path.
- **Alternatives:** Emitting `totalPages` from the API (rejected — redundant, and two sources of truth for a derived value invite exactly the drift that was observed); a `Link`/header-based pagination protocol (rejected — over-engineered for v1 scale).
- **Consequences:** `api-specification.md` §1 documents the envelope; the default `limit` for catalog/inventory is 20 (auth/user listings stay at 25). Tests stub the real contract (no `totalPages`), so a reintroduction would fail.

### D-22 · Catalog authorization & archival model — **Accepted** (Phase 5)
- **Context:** Products/inventory must be browsable by customers yet strictly protected from modification; inactive products must vanish from the public catalog but cannot be destroyed where orders reference them; stock changes must be transactional and audited.
- **Decision:** (1) Read endpoints `GET /api/products` and `GET /api/products/:id` use `optionalAuthenticate` — anonymous passes, and a recognized ADMIN bearer additionally reveals archived (`is_active=false`) rows; every other caller is force-filtered to active-only, and detail returns `404` (not `403`) for a hidden product so existence isn’t leaked. (2) All writes are ADMIN-only via `authorize('ADMIN')`; inventory reads are `authorize('ADMIN','ORDER_MANAGER')`; customers are never granted either. (3) **No DELETE route** — retirement is a soft archive (`PATCH {is_active:false}`); the RESTRICT FK from `order_items.product_id` makes physical deletion of a referenced product impossible at the DB. (4) Stock adjustment locks the row `SELECT … FOR UPDATE`, then writes the `inventory_movements` ledger row and a `STOCK_ADJUSTED` `audit_logs` row **inside the same `withTransaction`**; the service pre-checks non-negative physical/available and the DB `CHECK`s (SQLSTATE 23514) are the final guard, both mapping to a clean `409 INSUFFICIENT_STOCK`.
- **Alternatives:** `authenticate` on the public catalog (rejected — customers must browse without a session); returning `403` for inactive products (rejected — leaks which archived ids exist); a hard-delete admin endpoint guarded by a “has orders?” query (rejected — TOCTOU-prone; the soft-delete + RESTRICT FK is simpler and safer); checking stock without `FOR UPDATE` (rejected — concurrent adjustments could oversell between read and write).
- **Consequences:** FR-CAT-08 (“inactive products cannot be ordered”) is enforced at catalog level in Phase 5 (active-only listing + `404` on inactive detail); the cart/order rejection path lands with the cart module. The audit trail now has real `PRODUCT_CREATED`/`PRODUCT_UPDATED`/`PRODUCT_DEACTIVATED`/`STOCK_ADJUSTED` writers. Verified live: 66/66 smoke checks including DB proof that a refused oversell writes neither a movement nor an audit row.

### D-23 · Cart is a self-scoped, server-priced draft — never a stock reservation — **Accepted** (Phase 6)
- **Context:** FR-CART-01..05 require a persistent per-customer cart with correct totals, without ever promising stock that later orders might need (the top business risk R-01). A naive cart that trusts client prices or reserves on add would either mis-bill or freeze inventory.
- **Decision:** (1) **Ownership is the token, never the request** — cart endpoints carry no cart/customer id; `req.user.id` selects the single `carts` row (`carts.customer_id` UNIQUE), and every line read/write is scoped by it, so cross-customer access is structurally impossible and a foreign item id returns `404` (not `403`). Strict Zod schemas reject any client-supplied `customer_id`/`cart_id`/price field outright. (2) **A cart does not reserve stock.** Add/update only *reads* current `available_quantity` to reject an obviously-unfulfillable quantity (`409 INSUFFICIENT_STOCK`); it never locks or decrements. Because stock can fall after a line is added, every `GET /api/cart` recomputes live prices/availability and flags `stock_warning` (qty > on-hand) or `unavailable` (product deactivated) — checkout (Phase 7) re-verifies authoritatively under `SELECT … FOR UPDATE`. (3) **Server-derived money** — line totals/tax/subtotal/grand are computed from catalog NUMERIC via integer-cent math with half-up per-line rounding (D-09), so `grand = subtotal + tax` holds to the cent (AC-CART-02 fixture `19.99 × 3 @ 7.5% → 59.97 / 4.50 / 64.47`). (4) **Documented per-line max** of `1000` (`constants/cart.js`), mirrored as a DB `CHECK` (migration 15). (5) **Upsert merge** on `(cart_id, product_id)` means re-adding a product increases quantity instead of duplicating (FR-CART-01). Adding/patching an inactive/unknown product → `404 PRODUCT_NOT_FOUND` (completes FR-CAT-08).
- **Alternatives:** Trusting a client-sent subtotal (rejected — billing fraud/rounding drift); reserving stock on add-to-cart (rejected — abandoned carts would hold inventory and starve real orders, violating FR-CART-04); a cart id in the URL (rejected — reintroduces the IDOR surface the self-scoped design removes); storing prices on the cart line (rejected — a cart must reflect the *current* catalog until checkout snapshots it into `order_items`).
- **Consequences:** FR-CAT-08 is now complete (cart rejects inactive products, not just the catalog listing). New audit actions `CART_ITEM_ADDED/UPDATED/REMOVED` and `CART_EMPTIED` are written in the same transaction as each mutation. The order module must re-read the cart server-side and re-check stock — the cart is advisory only. Verified: 69/69 backend unit, 67/67 DB integration (incl. cross-customer isolation, no-reservation proof, and migration-15 reversibility), 32/32 frontend.

### D-24 · Five-state order lifecycle; reserve on create, consume at ship, release on cancel — **Accepted** (Phase 7)
- **Context:** Phase 7 must turn the (advisory) cart into a real, concurrency-safe order (risk R-01 is the top business risk), enforce the documented lifecycle (FR-ORD-07..11), and keep money exact, writes atomic and submissions idempotent. The committed schema and a passing Phase-3 test only allowed the legacy domain `pending/confirmed/fulfilled/cancelled` and asserted `shipped` was *invalid* — which directly conflicts with the richer chain the customer requested. The three decisions below (lifecycle shape, consumption point, invoice scope) were surfaced and the recommended option taken for each.
- **Decision:** (1) **Lifecycle** is the explicit one-step chain `pending → confirmed → processing → shipped → delivered`, plus `pending|confirmed → cancelled` as a *distinct* `POST /:id/cancel` operation (never a `PATCH` value); terminals have no outgoing edges and there are no skips or backwards moves. Migration 16 drops and re-adds the `order_status_valid` CHECK to the six-value set, **retiring `fulfilled`** (the earlier `db-integration` assertion that `shipped` violated the CHECK was updated to a still-invalid `archived`). The transition matrix is a single source of truth in `constants/orders.js`; the service re-checks every move and returns `409 INVALID_STATE_TRANSITION`. (2) **Stock is reserved on create and consumed exactly once at `shipped`** (D-18 model): create does `reserved += qty` under `SELECT … FOR UPDATE`; reaching `shipped` does `physical -= qty AND reserved -= qty` (a `fulfillment_consumption` movement); a pre-shipment cancel does `reserved -= qty` once (a `cancellation_release` movement). Because cancel is only legal from `pending|confirmed` and ship is the sole consumption point, **a unit can never be deducted twice**. Concurrency safety comes from locking inventory rows **one product at a time in ascending product-id order** (deadlock-free serialization) with the reservation/available `CHECK`s as the final oversell guard; availability is always re-read server-side, never trusting a prior cart/front-end check. (3) **Whole-order atomicity:** the order row, items (a historical snapshot — AC-ORD-06), stock reservations, the emptied cart and the audit row commit in ONE `withTransaction`; any shortfall (or inactive/unknown product) aborts the *entire* order with `409 INSUFFICIENT_STOCK`/`404` and leaves stock unchanged (AC-ORD-02). (4) **Idempotency** claims the key in a *separate committed transaction* before touching stock, stores a SHA-256 `request_hash` of the normalized (deduped, id-sorted) lines (new `idempotency_keys.request_hash` column, migration 16), replays a completed key’s stored body (`200 idempotent:true`), rejects a concurrent in-progress claim with `409 DUPLICATE_REQUEST`, refuses a reused key with a *different* body as `409 IDEMPOTENCY_CONFLICT`, and frees a failed claim for retry. (5) **Invoicing is deferred** to a later phase — shipping reserves+consumes but does not yet raise an invoice; §2.5 stays a forward-looking spec.
- **Alternatives:** Keeping the legacy 4-value enum (rejected — cannot express processing/shipped/delivered and the accepted `shipped`-consumes model); consuming stock at create (rejected — cancellations would then need a physical restore, reintroducing double-deduct risk); consuming at `delivered` (rejected — physical stock should leave the warehouse at shipment, the accounting-faithful point); a single bulk `WHERE product_id IN (…) FOR UPDATE` lock (rejected — lock-acquisition order across concurrent orders is then unpredictable and deadlock-prone versus the deterministic per-product ascending loop); folding cancellation into `PATCH status` (rejected — the customer explicitly asked for cancellation as a distinct, separately-authorized operation).
- **Consequences:** Migration 16 is reversible (up narrows nothing on empty tables; down restores the pre-Phase-7 CHECK), and the reversibility test now truncates order rows first so later suites’ lifecycle data can’t skew a DDL round-trip. New audit actions `ORDER_CREATED`/`ORDER_STATUS_CHANGED`/`ORDER_CANCELLED` and movement types `order_reservation`/`fulfillment_consumption`/`cancellation_release` are live. `POST /api/orders` is customer-only; `PATCH /:id/status` is ADMIN/ORDER_MANAGER-only; a customer may cancel only their own order (foreign → `404`). Verified: 79/79 backend unit, 85/85 DB integration (incl. a 20-way oversell race, idempotent replay + conflict, shortfall rollback, ship-consume and single-release cancel, snapshot immutability, and migration-16 reversibility), 46/46 frontend.

### D-25 · Invoice minted atomically at ship; `issued | voided`; print-CSS (no PDF); yearly counter — **Accepted** (Phase 8)
- **Context:** FR-INV-01..05 require a financial document for a fulfilled order with a race-safe unique number, drawn from the order's persisted snapshot (never the live catalog or a client body), idempotent under retries, ownership-scoped, and viewable on a professional printable page — while this remains a *simulated* business with no established tax compliance. Four design forks were surfaced and the recommended option taken for each.
- **Decision:** (1) **Trigger** — the invoice is minted *inside the same `withTransaction` that consumes stock at `→ shipped`* (the D-24 fulfillment point), so an invoice can never exist for an order that did not actually ship and never twice for one that did. `invoices.order_id` is `UNIQUE`; `insertInvoice` uses `ON CONFLICT (order_id) DO NOTHING` and the service replays the winner, making generation idempotent even for a concurrent double-ship (FR-INV-05 / AC-INV-03). (2) **Status** — `issued | voided` only (migration 17 adds the column, `DEFAULT 'issued'`, CHECK). `voided` is a staff-only annulment that *preserves the row and its denormalized totals* (financial immutability) and is audited; there is deliberately **no `paid`/`overdue`** state because settlement is out of scope (requirements §3.2 / D-14). Since an order can only be cancelled *pre-shipment* (D-24), a cancelled order simply has **no invoice** — cancellation never voids anything. (3) **Money** — the invoice copies `subtotal`/`tax_total`/`grand_total` straight from the order snapshot (integer-cent, D-09); `grand = subtotal + tax` is a DB CHECK, so a mismatched invoice cannot commit, and later catalog price edits can never alter an issued invoice (D-07 / SC-04 / AC-INV-01). (4) **Numbering** — `INV-YYYY-NNNNNN` drawn from a **per-calendar-year** counter row (`invoice_counters.period = 'YYYY'`) via an atomic upsert-RETURNING in the shipping transaction (FR-INV-02 / D-10); migration 17 *broadens* the period CHECK to `^[0-9]{4}(-[0-9]{2})?$` so the pre-existing monthly fixtures stay valid while the yearly key guarantees uniqueness of a year-only number. (5) **Reads** are ownership-scoped in the service — a customer sees only invoices of their own orders and a foreign id resolves to `404` (never `403`), staff (`ADMIN`/`ORDER_MANAGER`) see all; the sole write is the staff `POST /:id/void`. There is **no client path** to alter a total or ownership. (6) **Presentation** — the SPA renders a print stylesheet (`@media print`) with a Print / Save-as-PDF button and NO PDF library; every document carries a distributor block and an explicit `DEMONSTRATION DOCUMENT … NOT a legal tax invoice` banner (the `INVOICE_DEMO_NOTICE` / `DISTRIBUTOR` are also embedded in the API payload).
- **Alternatives:** Raising the invoice at `delivered` or `confirmed` (rejected — ship is the true fulfillment/stock-consumption point, so the invoice and the stock movement stay atomic); a `paid` state (rejected — settlement is explicitly out of scope); deleting rather than voiding (rejected — destroys financial history); a monthly counter for a yearly number (rejected — `INV-YYYY` collides across months within a year); `pg` advisory locks for numbering (rejected — the upsert-RETURNING row is already race-safe and simpler, D-10); a server-side PDF dependency (rejected — the customer asked to avoid a PDF library; print CSS is dependency-free and inspectable).
- **Consequences:** Migration 17 is reversible (its `down` restores the strict monthly CHECK and drops the status columns), and the reversibility test now truncates `invoice_counters` as well as orders so yearly rows drawn by the invoice suite can't fail the re-added monthly CHECK on `down`. New audit actions `INVOICE_ISSUED`/`INVOICE_VOIDED` are live. New endpoints `GET /api/invoices`, `GET /api/invoices/:id`, `GET /api/orders/:id/invoice` (reads) and `POST /api/invoices/:id/void` (staff write). Verified: 86/86 backend unit, 95/95 DB integration (incl. no-invoice-until-ship + atomic appearance, strictly-increasing yearly numbers, UNIQUE duplicate rejection, customer/staff scoping, void-then-refuse, customer-cannot-void, cancelled-has-no-invoice, snapshot immunity to price edits, and migration-17 reversibility), 56/56 frontend (incl. the 10 invoice view/ownership/void tests).

### D-26 · Append-only audit gains an `outcome` + auth/user events; ADMIN-only trail; role-scoped dashboard with *booked* (not revenue) value — **Accepted** (Phase 9)
- **Context:** FR-AUD-01..05 require an audit-friendly activity system covering product/inventory/order/invoice/user changes with a stored outcome, transactional writes, protection from modification/deletion, an ADMIN-only query, and a business dashboard — while remaining a simulation with **no payment processing**, so "revenue" would be a fabricated figure. Four forks were surfaced and the recommended option taken for each.
- **Decision:** (1) **Outcome + auth audit** — migration 18 adds `audit_logs.outcome` (`'success' | 'failure'`, `NOT NULL DEFAULT 'success'`, CHECK) plus a plain `created_at` index backing recent-events/date-range scans. Committed business writes are `'success'` (a failed mutation rolls its whole transaction back and leaves **no** row, so there is nothing to mark failed); `'failure'` is reserved for security-relevant attempts that carry *no* data change — a rejected login. Auth is now audited: `LOGIN_SUCCESS`, `LOGIN_FAILED`, `ACCOUNT_DISABLED_ATTEMPT`, `AUTH_TOKEN_REUSED`, and `USER_REGISTERED` (the latter written in its own transaction; the standalone auth attempts use the pool since there is no business transaction to bind to). `PRODUCT_ACTIVATED`/`PRODUCT_DEACTIVATED` now fire only on an actual `is_active` **flip**, and the order stock lifecycle emits `STOCK_RESERVED`/`STOCK_CONSUMED`/`STOCK_RELEASED` inside their transactions. The `details` JSONB is a small explicit allow-list — never a password, JWT, auth header or unnecessary PII (actor id + role identifies the subject). (2) **Administrative user changes** — new ADMIN-only `GET /api/users` (safe columns only; `password_hash` is never selected) and `PATCH /api/users/:id` restricted to `role`/`is_active`; the update and its `USER_ROLE_CHANGED`/`USER_STATUS_CHANGED` audit row commit in ONE transaction, with a **self-lockout guard** (an admin cannot demote or deactivate *their own* account — `409`). No-op bodies are not audited; registration stays the public CUSTOMER-only flow. (3) **Endpoint scoping** — the trail is exposed solely by `GET /api/audit-logs` (ADMIN-only, filterable by actor/action/entity/outcome/date-range, paginated, READ-ONLY — there is no create/update/delete route anywhere, and the DB trigger already forbids mutation). Reports are **separately scoped**: `GET /api/reports/dashboard` is ADMIN-only (it embeds the audit activity feed), while `GET /api/reports/order-summary` and `GET /api/reports/low-stock` are the ADMIN + ORDER_MANAGER staff view — the *same* order/inventory metrics **minus** the who-did-what history. (4) **Metric honesty** — the dashboard reports only stored figures. Order value is defined as **`booked_order_value` = SUM(grand_total) over NON-CANCELLED orders in the window** — booked *demand*, explicitly **not revenue** (the platform never captures payment, requirements §3.2), and no revenue figure is emitted at all. Low-stock is an instantaneous snapshot (`available_quantity <= low_stock_threshold`), and every payload carries `metric_definitions` + a `limitations` note; nothing is estimated or fabricated.
- **Alternatives:** Leaving `outcome` out and defaulting success silently (rejected — the requirement mandates storing an outcome and a rejected login is the one genuinely interesting non-write event); folding the audit feed into the staff summary so agents see who did what (rejected — FR-AUD-03 keeps history admin-only); reporting "revenue" from order totals (rejected — no settlement exists, so it would be a fabricated performance figure); a public `DELETE`/`PATCH` on audit rows (rejected — the whole point is immutability, enforced by the existing append-only trigger); letting an admin demote themselves (rejected — strands the last privileged actor).
- **Consequences:** Migration 18 is reversible (`down` drops the index and the `outcome` column). New endpoints: `GET /api/audit-logs`, `GET /api/reports/dashboard`, `GET /api/reports/order-summary`, `GET /api/reports/low-stock`, `GET /api/users`, `GET /api/users/:id`, `PATCH /api/users/:id`. Frontend: a role-aware `DashboardPage` (ADMIN calls the dashboard, ORDER_MANAGER calls the order-summary and never sees the feed), an ADMIN-only `AuditLogsPage` viewer with no mutation affordance, and an ADMIN `UsersPage` for the audited role/status change. Verified: 95/95 backend unit (incl. the audit action-registry + outcome-validation units), 112/112 DB integration (incl. the audit completeness matrix, ADMIN-only + append-only access control, failed-login `'failure'` rows, filter/pagination, dashboard/order-summary access gating + aggregation accuracy on an isolated window with order-value-is-not-revenue, user self-lockout + audited change + deactivating-blocks-login, and migration-18 reversibility), 63/63 frontend (incl. the 7 dashboard/audit view tests proving the agent gets no audit feed).

### D-27 · Dependency-advisory triage: accept dev/ops advisories, ship a clean production surface — **Accepted** (Phase 11)
- **Context:** Phase 11 was a security & dependency audit (`npm audit` across the root, backend and frontend workspaces) with no feature change. It surfaced advisories but a mandatory constraint (D-17) pins `node-pg-migrate` to v7 because v9+ is ESM-only and the backend must stay CommonJS; the frontend test runner `vitest` likewise has fixes only in a breaking major. The question was whether to force breaking upgrades or accept the flagged advisories, and how to keep that honest.
- **Decision:** Triage by **reachability**, not raw severity, and record the measured state. (1) **Production browser surface is clean** — `npm audit --omit=dev` on the frontend reports **0 vulnerabilities**; the flagged `@vitest/mocker` (moderate) and `tinypool` (critical) items live only in `devDependencies` (the Vitest harness), are never bundled into `dist/`, and require a trusted operator to feed malicious worker options — so they cannot be reached by any end user. (2) **Backend** reports **2 high** (`glob` CLI command-injection via `node-pg-migrate`), and because `node-pg-migrate` is a `dependency` it also shows under `--omit=dev`; however the advisory is specific to `glob`'s `-c/--cmd` shell execution, which the application **never invokes** — migrations run only through controlled `npm run db:migrate` scripts with no attacker-controlled input, on a developer/ops machine. (3) **No breaking upgrade is forced**: `node-pg-migrate@9` would violate the D-17 CommonJS pin, and `vitest@5` is a test-only breaking bump with zero production benefit. (4) The root workspace audits **0 vulnerabilities**. These advisories are therefore **accepted and tracked**, with a standing re-review trigger: revisit when a **non-breaking** patch satisfies the advisory, when a runtime dependency actually uses the vulnerable code path, or before any real (non-simulated) production deployment with untrusted input reaching migration tooling.
- **Alternatives:** Blind `npm audit fix --force` (rejected — upgrades `node-pg-migrate` to ESM-only v9, breaking the D-17 CommonJS convention, and jumps `vitest` a major, for advisories that are unreachable in how this app actually uses those tools); moving `node-pg-migrate` to `devDependencies` purely to silence `--omit=dev` (rejected as cosmetic — it does not change the CLI-reachability analysis and the migration CLI is legitimately invoked in the deploy image); ignoring the audit entirely (rejected — no durable record of what was accepted or why).
- **Consequences:** A durable, evidence-backed triage replaces an unreviewed red X in the tooling. The acceptance is *conditional* and re-examined whenever the reachability premises change. No shipped code or dependency version was altered by Phase 11; all quality gates were re-run green against the current tree (95/95 backend unit, 133/133 integration on the isolated `b2b_oms_test` DB, 74/74 frontend, ESLint 0 errors both ends, clean Vite build, Prettier clean).

### D-28 · Browser E2E tier on a name-guarded disposable DB; SPA-click navigation for protected routes; coverage measured, never gated — **Accepted** (Phase 12)
- **Context:** Phases 3–11 shipped unit (Node test runner) + REST/DB integration (Supertest + `b2b_oms_test`) and frontend component (Vitest + RTL) tiers, but no **browser** end-to-end automation. Phase 12 had to prove the full stack through the real React SPA across the ten critical journeys plus negative paths, add reproducible coverage, and honour two hard constraints: **never touch a production/dev database**, and **generate evidence only from actually-executed tests** with **no arbitrary coverage threshold that hides missing tests**. Three forks mattered: how to isolate the E2E database from a suite that must mutate seeded stock; how to navigate an SPA whose access token is held in memory only; and whether coverage should gate the build.
- **Decision:** (1) **A dedicated, name-guarded disposable database `b2b_oms_e2e`.** A new `e2e/` npm workspace runs Playwright (Chromium); its `globalSetup` recreates `b2b_oms_e2e` from scratch (DROP `WITH (FORCE)` → CREATE → migrate → seed) via `backend/scripts/db/bootstrap-e2e.js`, which **refuses any target whose name does not match `/^[a-z0-9_]*_e2e$/i`** — so it is structurally incapable of resetting `b2b_oms` or any non-`*_e2e` DB (verified this session: pointed at `b2b_oms` it aborts). The `webServer` launches the API with `DATABASE_URL` overridden to `b2b_oms_e2e` and `reuseExistingServer:false`, so E2E never reuses a dev server bound to development data; the negative/adversarial paths then hit the authoritative REST API directly (Bearer) so the browser cannot accept what the server rejects. (2) **Client-side navigation for protected routes.** The frontend keeps the JWT access token in memory and silently rehydrates from the HttpOnly refresh cookie on mount; a cold `page.goto` to a guarded route drops the token and races that rehydration, which intermittently bounced journey 8 to `/login`. Protected screens are therefore reached by **clicking** the navbar / row / "View invoice" links (SPA routing, no reload) — deterministic and faithful to real user behaviour; only public routes use a cold goto. Journey 10 (cross-customer denial) is made race-immune: whether the guard bounces to login **or** the ownership-scoped server returns `404`, the assertion is that none of the victim's email or invoice number ever renders. (3) **Coverage is measured, not gated.** `run-coverage.js` mirrors `run-integration-tests.js` (requires `DATABASE_URL_TEST`, migrates, sets `B2B_RUN_DB_TESTS=1`) so the *whole* suite — not just DB-less units — is instrumented; V8 lines **96.34%**, branches **87.57%**, functions **92.63%**. The frontend v8 block (`all:true`, `include: src/**`) reports **87.76% lines** and **deliberately omits `thresholds`**, so thin spots (`LoginPage.jsx`/`UsersPage.jsx`, covered instead by the browser journeys; `requestLogger.js`, non-reachable unless `REQ_LOG=1`) stay visible rather than hidden behind a green average. (4) **Evidence only from real runs**, with known-benign noise preserved: the `pg.pool.error … terminating connection due to administrator command` line emitted when the guarded bootstrap drops the disposable DB before tests is captured, not scrubbed.
- **Alternatives:** Reusing `b2b_oms_test` (or `b2b_oms`) for E2E (rejected — violates the never-touch-dev rule and the seeded-stock isolation the lifecycle assertions need); an unguarded reset of an arbitrary DB (rejected — a `DROP` on the wrong name is catastrophic, hence the `_e2e` name guard); cold `page.goto` navigation to protected routes (rejected — races memory-token rehydration and flakes, the exact journey-8 failure); a per-test DB snapshot/restore instead of one serial shared narrative (rejected as heavier for the same determinism; serial single-worker + fresh logins already makes reservation/lifecycle assertions stable); enforcing a minimum coverage % in CI (rejected per the task — a lucky floor hides untested branches; we report, we do not gate); adding a PDF/visual-snapshot assertion layer (rejected — out of scope, the invoice is print-CSS by D-25).
- **Consequences:** A third (browser) tier now guards the whole stack; the new dev-only tools are `@playwright/test` (audits **0 vulnerabilities**) and `@vitest/coverage-v8` (adds only a node to the already-accepted D-27 `vitest → @vitest/mocker + tinypool` dev chain; production `--omit=dev` stays **0**). Playwright's generated `playwright-report/` / `test-results/` are added to `.prettierignore` / `.gitignore` so machine output is neither formatted nor committed. Verified this session against the current tree, all green: **17/17 E2E** (10 journeys + 7 negative), **228/228 backend** across 39 suites (isolated `b2b_oms_test`, 96.34% lines), **133/133** DB integration subset, **74/74 frontend** (87.76% lines), ESLint 0 errors both ends, Prettier clean. The memory-token navigation constraint now documented here is a standing requirement for any future browser test. Plan + results + raw output live in `docs/test-plan.md`, `docs/test-results.md` and `evidence/test-reports/phase12-*`.

### D-29 · Production-shaped Compose with a one-shot migration service, secret-free images, and a dev-only host-port override — **Accepted** (Phase 13; **supersedes D-03's "migrations run by the api container on boot"**)
- **Context:** Phase 13 had to containerize the finished app for reproducible deployment without changing application behaviour, under hard constraints: no `.env`/secrets in images; nothing sensitive hardcoded; non-root where practical; do **not** publish PostgreSQL unnecessarily; run migrations as a **controlled deployment step, not independently from every backend replica**; wait for real DB readiness; preserve data across restarts; and never delete volumes/data automatically. The Phase-2-era `docker-compose.yml` violated several of these: it ran `migrate up && node server.js` inside the `backend` container (so every replica raced on `pgmigrations`), shipped a hardcoded `change-me-dev-only` password in `DATABASE_URL`, published PostgreSQL on host `5433` unconditionally, and had no frontend healthcheck.
- **Decision:** (1) **Split the stack into two files.** `docker-compose.yml` is the **production-shaped** topology (`db`, one-shot `migrate`, `backend`, `frontend`, plus an optional `seed` under `profiles: ['tools']`) that publishes **only** the browser port (`${WEB_PORT:-8080}:80`); `docker-compose.dev.yml` is a **local override** that adds the host-published `5433`/`4000` needed by host-side scripts, `vite dev` and the test suites — never applied in production. (2) **A dedicated one-shot `migrate` service** (`restart: 'no'`, `command: node scripts/db/migrate.js up`, `depends_on: db: {condition: service_healthy}`), and `backend` gated by `depends_on: migrate: {condition: service_completed_successfully}` **in addition to** `db: service_healthy`. The API `CMD` only starts the server. This makes readiness **enforced, not assumed**, and guarantees a **single** migration runner — proven by scaling `--scale backend=3`, which started 3 healthy API containers and still exactly one `migrate`. `pg_isready` (db) and HTTP `/api/health` (backend) healthchecks, plus nginx `/`+`/api/health` on the frontend, carry the ordering. (3) **No secrets in images, fail-fast at parse time.** Multi-stage builds (`node:20-alpine` deps→runtime for the API with `npm ci --omit=dev`; `node:20-alpine` build → `nginx:1.27-alpine` for the SPA) copy an explicit file list (no `COPY . .`); both `.dockerignore`s exclude `.env*`; required deployment values use `${VAR:?message}` so Compose **refuses to render** without `POSTGRES_PASSWORD`/`JWT_ACCESS_SECRET`/`JWT_REFRESH_SECRET`; the API runs as `USER node` (uid 1000). Defence-in-depth: `backend/src/config/env.js` still refuses to boot in `production` on a weak/short/dev-default secret or `COOKIE_SECURE=false`. (4) **Same-origin** is kept — the SPA calls relative `/api` and nginx proxies to `backend:4000`, so containers address each other **by service name** (`db:5432`, `backend:4000`) and no CORS is required. (5) **Data safety.** PostgreSQL lives in the named `pgdata` volume, which survives `down`/`stop`/rebuild; `down -v`, `volume rm`, `dropdb` and `db:migrate:down -- --all` are documented **only** as destructive, human-confirmed operations (`docs/deployment.md` §8) and are never wired into any script. Backup/restore is `pg_dump -Fc` + `pg_restore` **inside** the `db` container (no host client, no published port needed).
- **Alternatives:** Migrations on every API boot (rejected — the exact per-replica race the task forbids); an `entrypoint` that migrates then execs the server in the same container (rejected — same coupling, still one runner per replica); publishing PostgreSQL in the base file for convenience (rejected — the task requires it stay internal; a separate dev override layer gives host access only where intended); baking a `.env` or default password into the image / Compose (rejected — secrets are interpolated from the git-ignored root `.env` and validated fail-fast); running the API as root (rejected — `USER node`); a Kubernetes/Helm manifest (rejected as out of scope for a single-node reproducible deployment).
- **Consequences:** `docker compose up` is now a safe, ordered, reproducible deployment; scaling the API can no longer corrupt migration state; secrets cannot leak into an image and insecure values cannot boot the API. Deployment config, HTTPS expectations, secret management, backup/restore and operational limitations are documented in `docs/deployment.md`, summarised in the README Docker section, and evidenced at runtime in `evidence/test-reports/phase13-*`. **Runtime verification was performed (Docker was available)**: clean build → readiness ordering → 18 migrations/14 tables on an empty volume → idempotent migrate → seed → data preserved across a full `down`/`up` → `pg_dump`/`pg_restore` round-trip → a **9/9** `scripts/deploy-smoke.js` through the browser origin, all in isolated Compose projects that left the development database untouched. This surfaced and fixed one genuine production defect the container path could catch but no host-side test could: **`bcryptjs` was declared a `devDependency` while being required at runtime**, so the `--omit=dev` image crashed with `Cannot find module 'bcryptjs'`; it is now in `dependencies` and the lockfile regenerated. Remaining limitations are documented (HTTPS not terminated in-container; `nginx:1.27-alpine` keeps a root master with unprivileged workers; base images pinned to tag not digest; single-node, no registry/CI; in-process rate limiting and in-memory access tokens; `e2e` Playwright tier still host-run, not containerized).
